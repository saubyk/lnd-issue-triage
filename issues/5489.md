## Summary
Feature request (Jul 2021, lnd 0.13.x on iOS via the mobile bindings): the
`StopDaemon` RPC returns as soon as shutdown is *requested*, not when it is
*complete*, so a mobile app has no way to know when lnd has fully stopped.
Relaunching while the previous instance is still winding down crashes the app.
The reporter asks for a way to observe shutdown through to completion;
Roasbeef suggested an optional blocking flag on `StopDaemon`. On master
`StopDaemon` is still fire-and-forget and nothing exposes a "stopped" state.
The gap is real, and a second mobile wallet developer (Blixt) re-raised the
exact same problem in Feb 2026 on PR #4595, which now has two maintainer
approvals but is not merged. The reporter's secondary point about wallet
unlock racing with the first RPC call was addressed by the State service in
v0.13.0.

## Evidence
- Thread: Roasbeef (MEMBER), 2021-07-10: "one option here is to optionally
  make the shutdown call blocking. A new flag can be added the listens on the
  normal shutdown channel until it's sent upon which signals that everything
  has wrapped up." Never implemented. No cross-referenced PRs on the issue.
- Primary ask, shutdown state. `rpcserver.go:6792-6824` on master:
  `StopDaemon` calls `r.interceptor.RequestShutdown()` and immediately returns
  `Status: "shutdown initiated, check logs for progress"`. `StopRequest` has no
  blocking/wait field (`lnrpc/lightning.proto:385-389`). The `WalletState`
  enum served by `GetState`/`SubscribeState` has no stopping/stopped value
  (`rpcperms/interceptor.go:305-328`: WAITING_TO_START, NON_EXISTING, LOCKED,
  UNLOCKED, RPC_ACTIVE, SERVER_ACTIVE).
- Mobile bindings, `mobile/bindings.go:91-156`: `Start` runs `lnd.Main` in a
  goroutine and closes a local `quit` channel when it returns, but the only
  callback fired is `rpcReady.OnResponse` when the RPC listener is up. Nothing
  is fired when `lnd.Main` returns, and the `lndStarted` guard is not exported.
  So an app cannot tell when it is safe to call `Start` again.
- Same problem reported again: PR #4595 "mobile: Add ServiceStatus for
  retrieving started up status of lnd" (hsjoberg, opened 2020-09-04, reopened
  2026-02-19). hsjoberg's comment of 2026-02-19: "`stopDaemon` returns
  immediately and does not wait for the gRPCs to close down ... there is no
  good way to tell when it's possible to start lnd up again." It exports a
  `ServiceStatus` gomobile function so the app can poll whether lnd is still
  running. Approved by Roasbeef (2026-02-20) and bhandras (2026-03-27); still
  open, bot re-request-review reminders weekly through 2026-10-26, mergeable
  state UNKNOWN. Touches only `mobile/bindings.go`. This solves the mobile
  case by polling; it does not add a blocking `StopDaemon` or a shutdown state
  to the State service, so non-mobile gRPC clients are unaffected.
- Related history: #4492 (hsjoberg, closed 2021-04-15) fixed the crash on
  restart after `stopDaemon` via #4590 (signal state cleanup), #4591 (unload
  wallet on shutdown) and #4599 (falafel listeners). Those make restart *work*
  once lnd has fully stopped; they do not tell the caller *when* it has.
- Secondary ask, wallet unlock race (reporter's comment 2021-07-22): fixed by
  the State service, PR #5005 (halseth, merged 2021-03-18, v0.13.0; commit
  `9ef556624` "lnrpc: add StateService"). `SubscribeState` emits UNLOCKED ->
  RPC_ACTIVE -> SERVER_ACTIVE; a client that waits for RPC_ACTIVE before
  calling `AddInvoice` no longer sees "wallet locked". The reporter was on
  0.13.x so this already existed; they were likely not using it.
- Other related, not duplicates: PR #8659 "signal: manage shutdown requests
  with status codes" (closed for inactivity 2024-11-12) was about process exit
  codes, not RPC-observable shutdown completion. #10044 (merged 2025-07-08)
  fixed a shutdown deadlock, unrelated to signalling.
- Duplicate search ("StopDaemon blocking", "shutdown state mobile", "stop
  wait until shutdown complete"): no newer *issue* tracks this. The active
  tracker is PR #4595.
- No reproduction attempted: this is a feature gap, confirmed by reading the
  code paths above.

## Assessment for the human
Still valid: the exact gap the reporter described exists on master and a
second mobile wallet team hit it in 2026. Product questions:
1. Is PR #4595 the intended answer? It has two approvals and only needs a
   merge (or a rebase). If so, this issue should be linked from the PR and
   closed when it merges. It covers the mobile bindings only.
2. Does lnd also want the general gRPC solution Roasbeef proposed in 2021
   (an optional `wait`/blocking flag on `StopDaemon`, or a STOPPING/STOPPED
   value in `WalletState`)? That would help any client, not only gomobile
   apps, but a blocking `StopDaemon` has the catch-22 hsjoberg notes: the
   gRPC server is torn down during shutdown, so the response may never be
   delivered. A new State value sent before the RPC server stops is the
   cleaner shape, if wanted.
3. Housekeeping: the issue is labelled `rpc`, `feature request`, `P3`, no
   assignee, no milestone, last activity 2021. Worth retitling to "Expose
   shutdown completion (blocking StopDaemon or shutdown state)" and linking
   #4595 so the two threads stop living apart.

## Optional status comment
Status check against current master: still open. `StopDaemon` still returns
as soon as shutdown starts, and there is no state an app can watch to learn
when lnd has fully stopped. PR #4595 adds a `ServiceStatus` call to the mobile
bindings for exactly this purpose and has two maintainer approvals but is not
merged yet. The separate point about the wallet-unlock race is covered by the
State service (`SubscribeState`, in lnd since v0.13.0): wait for `RPC_ACTIVE`
before making other calls.
