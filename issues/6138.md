## Summary
Bug report (Jan 2022, lnd 0.14.1): with Prometheus monitoring enabled, lnd
exports every `etcd_*` metric series even when the node uses bbolt, so stock
etcd alerts such as `etcd_server_has_leader == 0` fire. Roasbeef confirmed the
cause (release builds include the `kvdb_etcd` tag and an `init()` in the etcd
import path registers the metrics) and suggested rebuilding without the tag.
Still reproducible on master: the embedded-etcd support, which pulls in the
etcd *server* package and its 68 metric families, sits behind the same build
tag that release binaries ship with. The fix is small (gate the embedded
server behind its own tag or drop it from release builds), but etcd is not
where database work is going: the SQL migration targets sqlite and postgres,
and bbolt/etcd are expected to reach end of life when it completes. Whether
to spend effort on an etcd-adjacent cosmetic fix is a product call.

## Evidence
- Thread: Roasbeef (MEMBER), 2022-01-06: "We build with it on by default
  now, which may end up exporting those metrics. You can re-build with the
  tag off if you aren't using it at all." 2022-01-08: "I'm assuming there's
  an `init()` func somewhere in the module import path that automatically
  registers the etcd metrics..." Reporter had stopped building their own
  binaries. Labels `monitoring`, `P4`, `etcd`. No cross-referenced PRs, no
  activity since 2022-01-17.
- Root cause on master:
  - `make/release_flags.mk:67` still ships `kvdb_etcd` in `RELEASE_TAGS`.
  - `kvdb/etcd/embed.go` (`//go:build kvdb_etcd`) imports
    `go.etcd.io/etcd/server/v3/embed` to support `db.etcd.embedded`, which
    `sample-lnd.conf:1664-1666` describes as "Useful for testing". The client
    library alone would not do this; it is the embedded *server* that drags in
    `go.etcd.io/etcd/server/v3/etcdserver`.
  - `etcdserver/metrics.go:180` (etcd v3.5.12, `go.mod:173`) has
    `func init() { prometheus.MustRegister(hasLeader) ... }`, registering into
    the global default registry.
  - `monitoring/monitoring_on.go:46` serves `promhttp.Handler()`, which is
    the default registry, so everything registered globally is exported.
  - `go list -deps` with the release tags on `./cmd/lnd`: 40 packages under
    `go.etcd.io/etcd/server/v3` are linked, including `etcdserver` and
    `embed`. Without `kvdb_etcd`: 0.
- Context from the PM (not yet stated in release notes or docs on master):
  the etcd backend is not actively maintained; the native-SQL migration
  (epic #10680, channel state and forwarding log, after graph, payments and
  invoices) targets sqlite and postgres; bbolt and etcd are expected to be
  end-of-life once it completes. No public deprecation notice for etcd exists
  yet (`docs/release-notes/release-notes-0.21.0.md` Deprecations section
  covers only `lnrpc.Hop` fields and `--sat_per_byte`).
- Duplicate search ("etcd metrics prometheus", "etcd deprecate"): no other
  issue or PR. #10787 (make native SQL mandatory on sqlite/postgres) is the
  nearest related open item.
- Workarounds available today without rebuilding: drop the series in
  Prometheus scrape config (`metric_relabel_configs` with
  `regex: 'etcd_.*'`, `action: drop`), or scope etcd alert rules to jobs that
  actually run etcd.

## Assessment for the human
Technically still valid and cheap to fix: put `embed.go` behind a separate
tag (for example `kvdb_etcd_embedded`) that is only added for itests and dev
builds, and release binaries would stop linking the etcd server and its
metrics. Risk is low; the embedded server is documented as a testing aid.
Against that: etcd is a de-emphasised backend, the issue is P4 cosmetic noise
in monitoring, nobody has asked for it in almost four years, and operators
can drop the series in their Prometheus config. Options:
1. Close as not planned with the comment below (my recommendation if etcd is
   indeed winding down). Note the comment should not announce an etcd
   deprecation that has not been published; it says where database work is
   focused, not that etcd is removed.
2. Keep open as a good-first-issue sized cleanup if someone wants release
   binaries to stop shipping the embedded etcd server at all. That has a
   side benefit of a smaller binary and fewer linked dependencies.

## Draft comment
Closing this as not planned. The behaviour is still there: release builds
include etcd support, and the embedded etcd server that comes with it
registers its Prometheus metrics at startup whether or not etcd is in use,
which is why a bbolt node reports `etcd_server_has_leader` as 0. Database
work in lnd is now going into the SQL backends (sqlite and postgres) rather
than etcd, so changing how the etcd build is packaged is not something we
plan to pick up. If the stray series are a problem for your alerting, the
practical fix is on the Prometheus side: drop `etcd_.*` for the lnd job with
`metric_relabel_configs`, or restrict the etcd alert rules to the jobs that
actually run etcd. Building lnd without the `kvdb_etcd` tag also removes them
entirely.
