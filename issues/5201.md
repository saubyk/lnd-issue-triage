## Summary
QueryRoutes for a circular route (target = self) returns routes whose last hop
is one of our own channels where the peer's remote balance is smaller than the
amount. lnd knows that balance but pathfinding only consults live balance for
channels leaving our node, never for channels coming back in. Unchanged on
master. carlaKC (2021-04-22) described the fix: look up incoming balance the
same way outgoing balance is looked up and feed it to pathfinding.

## Evidence
- `routing/unified_edges.go:57`: `localChan := fromNode == u.sourceNode`.
  Only edges whose *source* is our node are treated as local.
- `routing/unified_edges.go:219-229`: `getEdge` calls `getEdgeLocal` (which
  checks `bandwidthHints.availableChanBandwidth`, `:295-322`) only when
  `localChan` is true; every other edge goes through `getEdgeNetwork`, which
  uses policy and capacity only.
- The final hop of a circular route is the edge peer -> self. Its source is the
  peer, so it is a network edge and gets no balance check. The route in the
  report (last hop over a channel with remote_balance 30,099 sat for 66,029
  sat) is still produced today.
- `routing/bandwidth.go:53-84` and `:192-210`: the bandwidth manager only
  registers outbound channels of the source node and reports
  `link.Bandwidth()`, i.e. our outgoing capacity. There is no notion of
  incoming bandwidth (the peer's balance) anywhere in `routing/`.
- `routing/pathfind.go:1054` handles `routeToSelf` explicitly, so self-routes
  are a supported, first-class case, not an accident.
- No PR or newer issue addresses this. gh searches for incoming bandwidth /
  inbound liquidity / remote balance in pathfinding return nothing. Release
  notes have no matching entry.
- Reporter's own workaround (C-Otto/rebalance-lnd#150) was client-side
  filtering of candidate channels, which any app can do by reading
  `remote_balance` from `ListChannels` and passing `last_hop_pubkey` /
  `ignored_pairs` to QueryRoutes.

## Assessment for the human
The gap is real and cheap to close: for the final hop of a `routeToSelf`
search, consult the local channel's remote balance (minus the peer's reserve
and in-flight HTLCs) the way `getEdgeLocal` consults our outgoing bandwidth.
Rebalancing tools all hit this. If the product call is to leave it to
applications, the workaround above is complete and a not-planned close is
defensible; a draft for that case is below. Otherwise keep open as
`still-valid`, no comment needed.

## Decision
Closed as not planned on 2026-09-16: left to applications via ListChannels +
last_hop_pubkey / ignored_pairs.

## Draft comment
Closing this as not planned. When lnd searches for a route, it only checks live channel balances for the first hop, the channel the payment leaves through. For every later hop, including the last hop back into your own node, it can only go by channel capacity, because that is all the network graph tells it. The information you need to avoid this is already available to you: read remote_balance for your channels from ListChannels and pass a suitable last_hop_pubkey, or exclude the channel through ignored_pairs, when you call QueryRoutes. That is what rebalancing tools do today.
