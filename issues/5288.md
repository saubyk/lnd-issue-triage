## Summary
Request (May 2021): add optional random delay ("jitter") when lnd forwards a
payment, so a node on the route cannot use message timing to work out where a
payment starts or ends. lnd has not added this. Since the request, the
protocol discussion has moved away from forwarding delays: the 2025 spec
discussion preferred delays at the receiver, and the new "attribution data"
feature makes each node report how long it held a payment so senders can
penalise slow nodes. A node operator who wants jitter can already add it from
outside lnd with the HTLC interceptor. Whether to close or keep this is a
product call.

## Evidence
- Thread: labels `brainstorming`, `feature request`, `htlcswitch`, `P3`. Two
  comments, both May 2021. carlaKC (COLLABORATOR) did not decline; she said
  lnd would not add it "if we're not certain that it will have the desired
  privacy gain" and asked the reporter to research what jitter would be
  effective. The reporter said "eventually"; nothing followed. No
  cross-references.
- No jitter on master: no match for jitter / random delay / forwarding delay
  in `htlcswitch/`. The only timing knob is `channel-commit-interval`
  (`config.go:472`, default 50ms, `sample-lnd.conf:396`), a fixed batching
  window that is not randomised.
- Application-level route exists: `routerrpc.HtlcInterceptor`
  (`lnrpc/routerrpc/router.proto:140`) hands each forwarded HTLC to an external
  program, which can hold it and resume it later. A program that resumes after
  a random delay is the lnd equivalent of the C-Lightning plugin the reporter
  linked (which is also a plugin, not core).
- Spec direction, lightning/bolts#1263 "Add recommendations for receiver-side
  random delays" (tnull, opened 2025, still open, concept ACK from t-bast):
  "there was agreement from multiple sides that receiver-side delays were
  preferable to forwarding delays", partly because several hops each adding
  their own delay makes it hard to reason about the result. Links the Delving
  thread "Latency and Privacy in Lightning".
- Attribution data, lightning/bolts#1044, merged 2025-11-18: each hop reports
  its HTLC hold time, and BOLT 4 (master `1aadb719b`, line ~1225) says "The
  origin node can use this information to score nodes on latency." A node
  that adds forwarding jitter would report, or be assigned, higher latency.
  lnd's implementation is PR #9888 "Attributable failures", open, milestone
  v0.22.0, last updated 2026-09-28.
- The spec's existing "SHOULD add a random delay" wording (BOLT 2 ~line 2988,
  BOLT 4 ~lines 304 and 581) covers failures on blinded paths only, not
  forwarding in general.
- No newer lnd issue or PR found for jitter, timing attack, forwarding delay,
  random delay or hold time, other than #9888.
- No reproduction: this is a design request, not a bug.

Confidence is medium because the spec-side picture is read from PR
descriptions and the merged spec text; the Delving thread and spec meeting
notes were not read in full, and bolts#1263 is not merged.

## Assessment for the human
Product questions:
1. Does lnd want forwarding jitter at all? It trades payment speed and
   locked liquidity for a privacy gain that nobody has quantified (carlaKC's
   2021 objection still stands), and from v0.22 attribution data would let
   senders penalise a node that delays forwards. Routing-node operators are
   the users most likely to object.
2. Is the application-level answer enough? The interceptor lets an operator
   who wants jitter add it today without lnd carrying the feature.
3. Should lnd track the direction the spec did favour, a random delay at the
   receiver before settling or failing (bolts#1263)? lnd has no issue for
   that. If it matters for the roadmap, a fresh, narrowly scoped issue is
   cleaner than keeping this one, which asks for the approach the spec
   discussion moved away from.

Options:
- Close as not planned (recommended; draft below).
- Keep open as `brainstorming`: defensible only if forwarding jitter is still
  on the table for lnd.

## Decision
Closed as not planned on 2026-09-30: forwarding jitter left to applications via
HtlcInterceptor; spec direction is receiver-side delays. Comment posted.

## Draft comment
Closing this as not planned. Adding random delay to forwarded payments slows every payment through the node and keeps funds locked for longer, and it has not been shown to give a reliable privacy gain. The protocol discussion has since moved towards adding delay at the receiving node instead (lightning/bolts#1263), and the new attribution data feature lets senders see how long each node held a payment and favour faster nodes. A node operator who still wants forwarding jitter can add it today with an external program using the `HtlcInterceptor` RPC, which can hold each forwarded payment and release it after a delay of its choosing.
