## Summary
Alice -> Bob (public 0.02) -> Carol over two private 0.01 channels; Alice
pays 0.015 with max_parts=2. Reporter (ellemouton, on 0.12.1) saw intermittent
FAILURE_REASON_TIMEOUT and concluded it was nondeterministic, "maybe this
isn't an issue". Reproduced on current master with an itest: 2 of 6 runs
fail. The mechanism is a three-way interaction that is all still present:
Bob's non-strict forwarding picks the same private channel for two shards
that arrive in one batch, mission control then penalizes the Bob->Carol
*node pair* (so both hop hints are dead for that amount), and with
max_parts=2 the last-shard rule forbids splitting further, so the payment
reports no route while the first shard sits held at Carol until the MPP
timeout. Roasbeef's 2021 diagnosis ("splitting algorithm isn't aware of its
own in-flight shards") is still accurate. Since Feb 2026 this issue also
absorbs #4203 (closed as its duplicate by litbot) as the tracker for MPP
splitting-strategy improvements.

## Evidence
- Reporter's thread: Roasbeef (2021-03-02) suspected non-strict forwarding
  plus node-level penalization and named the broader gap: the splitter does
  not account for in-flight shards. ellemouton (2021-03-03) confirmed it is
  nondeterministic. No further activity; no linked PR.
- Code paths on master that produce the failure:
  - `routing/payment_session.go:399-406`: `isLastShard := activeShards+1 >=
    p.payment.MaxParts` -> "not splitting because shard limit reached" ->
    `errNoPathFound`. With max_parts=2 and one shard in flight, the remaining
    amount may never be halved.
  - `routing/missioncontrol.go` reports failures per node pair
    (`Reporting pair failure ... pair=Bob -> Carol`), not per channel, so a
    TemporaryChannelFailure on one private Bob->Carol channel penalizes both
    hop hints for that amount.
  - Bob's switch: both shards in the same batch query the outgoing link for
    the same chanID; the second add fails at the link with "commitment
    transaction dips peer below chan reserve" instead of being retried over
    the sibling channel (see Bob log excerpt below).
- Related: #7311 (open, 2023) "no fast payment failure for insufficient
  receiver liquidity" is the same family (MPP keeps splitting / waits for MPP
  timeout instead of failing fast). #4203 was closed 2026-02-21 as a
  duplicate of this issue.
- Payment lifecycle was refactored in 0.18 (#8174 family) and 0.19.3 fixed a
  same-route retry loop (#10125); neither touched the three mechanisms above.

```go
package itest

import (
	"github.com/btcsuite/btcd/btcutil/v2"
	"github.com/lightningnetwork/lnd/lnrpc"
	"github.com/lightningnetwork/lnd/lnrpc/routerrpc"
	"github.com/lightningnetwork/lnd/lntest"
	"github.com/stretchr/testify/require"
)

// testIssue5062MppMaxPartsTwo reproduces lightningnetwork/lnd#5062:
//
//	                   0.01 (private) -- Carol
//	Alice -- 0.02 -- Bob
//	                   0.01 (private) -- Carol
//
// Alice pays a 0.015 BTC invoice from Carol with max_parts=2. The invoice
// carries two hop hints (one per private channel). The report says this fails
// with FAILURE_REASON_TIMEOUT on 0.12.1 while max_parts=16 succeeds in 2 parts.
func testIssue5062MppMaxPartsTwo(ht *lntest.HarnessTest) {
	const (
		chanAB = btcutil.Amount(2_000_000)
		chanBC = btcutil.Amount(1_000_000)
		payAmt = int64(1_500_000)
	)

	alice := ht.NewNodeWithCoins("Alice", nil)
	bob := ht.NewNodeWithCoins("Bob", nil)
	carol := ht.NewNode("Carol", nil)

	ht.EnsureConnected(alice, bob)
	ht.EnsureConnected(bob, carol)

	cpAB := ht.OpenChannel(alice, bob, lntest.OpenChannelParams{
		Amt: chanAB,
	})
	cpBC1 := ht.OpenChannel(bob, carol, lntest.OpenChannelParams{
		Amt: chanBC, Private: true,
	})
	cpBC2 := ht.OpenChannel(bob, carol, lntest.OpenChannelParams{
		Amt: chanBC, Private: true,
	})

	ht.AssertChannelInGraph(alice, cpAB)

	resp := carol.RPC.AddInvoice(&lnrpc.Invoice{
		Memo:    "issue 5062",
		Value:   payAmt,
		Private: true,
	})
	decoded := alice.RPC.DecodePayReq(resp.PaymentRequest)
	require.Len(ht, decoded.RouteHints, 2, "expected two hop hints")

	payment := ht.SendPaymentAssertSettled(alice, &routerrpc.SendPaymentRequest{
		PaymentRequest: resp.PaymentRequest,
		MaxParts:       2,
		FeeLimitMsat:   noFeeLimitMsat,
		TimeoutSeconds: 60,
	})

	succeeded, failed := 0, 0
	for _, h := range payment.Htlcs {
		switch h.Status {
		case lnrpc.HTLCAttempt_SUCCEEDED:
			succeeded++
		case lnrpc.HTLCAttempt_FAILED:
			failed++
		}
	}
	ht.Logf("issue5062: payment %v settled with %d succeeded and %d "+
		"failed HTLC attempts", payment.PaymentHash, succeeded, failed)
	require.Equal(ht, 2, succeeded, "expected exactly two settled shards")

	ht.CloseChannel(alice, cpAB)
	ht.CloseChannel(bob, cpBC1)
	ht.CloseChannel(bob, cpBC2)
}
```

## Recommendation
Keep open. It is a real, reproducible pathfinding defect on master, it now
carries #4203's splitting-strategy discussion, and the reporter is a
maintainer who can be pinged with the reproduction. Useful next step for a
contributor: teach the payment session to avoid reusing a hop hint that
already carries an in-flight shard (Roasbeef's suggestion), or let the last
shard fall back to splitting when the failure was a liquidity failure on a
hinted private channel.
