## Summary
Question (Sep 2021, naveensrinivasan, same supply-chain batch as #5728, #5787
and #5944). The documented check for the Docker image,
`docker run --rm --entrypoint="" lightninglabs/lnd:<tag> /verify-install.sh <tag>`,
runs a script that ships *inside* the image it is verifying. The reporter
asked: (1) what if someone with Docker push access ships a tampered image
with a tampered script, and (2-3) what about a compromised Alpine base layer?
Roasbeef answered (1) in-thread: the in-image check does assume the script
wasn't modified, and proper image signing would fix that. Image signing is
tracked in #5728 (open since 2021). Its PR #5818 has been dormant since 2023,
after guggero argued keyless cosign adds little and Roasbeef later called it
"actually pretty useful". (2-3) is real and unaddressed: the script verifies
only `lnd` and `lncli`, not the base layer. The base is now partly covered by
#11437 (pin the alpine base), filed today. There is already a way to verify
without trusting the image, which I tested on v0.21.5-beta: copy the binaries
out and run the repo's `scripts/verify-install.sh` on the host. It isn't
documented. Recommend closing as answered, giving that recipe and pointing at
#5728 and #11437.

- Docs on master `c03d36598` still give only the in-image flow:
  `docs/DOCKER.md:60-72` (example tag `v0.14.1-beta`) and
  `docs/release.md:94-106` (example tag `v0.12.1-beta`). Both example tags
  are stale.
- `Dockerfile` copies `scripts/verify-install.sh` and `scripts/keys/*` into
  the image and writes `/shasums.txt` at build time. The script's
  `/shasums.txt` check (`verify-install.sh:244-250`) only proves the binary
  hasn't changed since the image was built, which is meaningless if the image
  is the thing that was tampered with.
- `scripts/verify-install.sh` accepts explicit paths: `verify-install.sh
  <version> [lnd-binary lncli-binary]` (:265-306). Keys come from
  `scripts/keys/` next to the script, so running it from a repo checkout uses
  keys from git, not from the image.
- Image signing: #5728 (open, no maintainer comments). PR #5818 "docker: Sign
  docker images without keys and push to ghcr.io" (open, adds
  `.github/workflows/docker-sign.yml`). guggero (2021-12-21): keyless
  signing only proves GitHub built it, while lnd's trust model is multi-party
  developer sign-off. Roasbeef (2023-08-01): "actually pretty useful" after
  the btcd version (btcsuite/btcd#1830). Then a bot inactivity close loop,
  muted by guggero 2024-01-29. `.github/workflows/docker.yml` on master has no
  signing step.

## Reproduction
Host-side verification of the published image, without trusting anything in
it except the two binaries. Run on macOS, 2026-10-28, with
`lnd/scripts/verify-install.sh` from master `c03d36598` (keys from git).

```
tag=v0.21.5-beta     # latest release
docker pull --platform linux/amd64 lightninglabs/lnd:$tag
id=$(docker create --platform linux/amd64 lightninglabs/lnd:$tag)
docker cp $id:/bin/lnd ./lnd; docker cp $id:/bin/lncli ./lncli; docker rm $id
lnd/scripts/verify-install.sh $tag ./lnd ./lncli
```

| case | result |
|---|---|
| binaries from the image | `SUCCESS! Verified lnd and lncli against manifest-v0.21.5-beta.txt signed by 5 developers.` exit 0 |
| `lnd` with one byte appended | `Your binary's hash does not match the expected release binary hashes.` exit 1 |

Not covered: arm64 image (only amd64 pulled). The base layer is not verified
by this or any other lnd check. A user should run the script from the release
tag's checkout rather than master. Since the release manifest is
signed, any script version with the right keys works.

## Draft comment
Proposed close as answered:

> Closing this, since the question was answered and the remaining work is
> tracked elsewhere. You're right that the script inside the image can't vouch
> for the image itself. To check the binaries without trusting the image, copy
> them out (`docker create`, then `docker cp <id>:/bin/lnd .` and the same for
> `lncli`) and run `scripts/verify-install.sh <version> ./lnd ./lncli` from a
> checkout of the lnd repository on your own machine. It checks them against
> the release signatures from the lnd developers. This only covers `lnd` and
> `lncli`, not the Alpine base. Signing the images themselves is tracked in
> #5728, and pinning the Alpine base image in #11437.
