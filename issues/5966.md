## Summary
Request (Nov 2021, naveensrinivasan, part of a batch of OpenSSF-style
security-hygiene filings against lnd): consider the binary hardening flags
Arch Linux proposed to the CNCF (RELRO, stack canary, NX, PIE, no RPATH, no
symbols, FORTIFY, plus `-trimpath`, `-mod=readonly`, external linking). The
issue is a copy of the CNCF discussion with no lnd-specific analysis, has no
comments, and the upstream CNCF issue it links was closed for inactivity in
2023 without producing a recommendation. Most of the listed flags do not
apply to lnd's release binaries, which are statically linked Go executables
built with `CGO_ENABLED=0`. Of the rest, lnd already strips symbols and uses
`-trimpath`. The only open item is PIE on Linux, which I tested on master: it
works and stays reproducible, but it costs 10% binary size and turns the
"statically linked" Linux binary into one that needs the glibc dynamic
loader, which the Alpine-based Docker image does not have. Product call.

## Evidence
- Thread: no comments, no cross-references, labels `golang/build system`,
  `security`. Reporter was a `CONTRIBUTOR` who filed ~20 security-process
  items in Nov 2021 (#5944 dependency policy, #5889 vendored actions, #6009
  sigstore, #5965 ClusterFuzzLite, ...). Most are closed; #5889 and #5944
  remain open.
- Upstream source: cncf/tag-security#422 closed 2023-07-31 "due to
  inactivity" after a maintainer noted a CNCF-wide flag mandate "may not be
  achievable, given that every project makes its own technical choices".
- Current release build on master (`scripts/release.sh:208-209`,
  `Makefile:67,178-179`): `CGO_ENABLED=0 go build -trimpath
  -ldflags="-s -w -buildid= -X ...Commit=..."`. So, against the list:
  - `-trimpath`: already used (also required for reproducible builds,
    `docs/release.md`).
  - No symbols: already done, `-s -w` strips the symbol table and DWARF.
  - No RPATH, FULL RELRO, FORTIFY: these are properties of dynamically linked
    C binaries (RPATH/RELRO concern the dynamic loader and GOT; FORTIFY
    replaces libc calls at compile time). A `CGO_ENABLED=0` Go binary has no
    libc, no GOT and no RPATH, so there is nothing to harden here.
  - Stack canary: a C compiler mitigation. Go has no equivalent flag; the
    runtime uses bounds-checked slices and growable stacks instead.
  - NX: the Go linker already marks the stack non-executable on Linux and
    sets `NX_COMPAT` on Windows (verified below).
  - `-mod=readonly`: the default since Go 1.16 whenever `go.mod` exists.
  - `-linkmode=external` and `CGO_ENABLED=1`: the opposite of lnd's
    deliberate choice. The release build uses `CGO_ENABLED=0` precisely so the
    binaries are static and reproducible across build hosts.
  - PIE: the one real gap on Linux. See reproduction below.
- Windows and macOS releases are already position independent by default
  (Go has defaulted to PIE on windows since Go 1.15 and darwin/arm64 is
  always PIE). Verified on master builds: `otool -hv` on a darwin/arm64 lncli
  shows `PIE`; the windows/amd64 lncli PE header has DllCharacteristics
  0x8160 = DYNAMIC_BASE + HIGH_ENTROPY_VA + NX_COMPAT.
- Linux release binaries are not PIE: `file` on a linux/amd64 lnd built with
  the release flags reports "ELF 64-bit LSB executable ... statically linked,
  stripped".
- Docker: `Dockerfile:26` runs lnd on `FROM alpine as final`, built via `make
  release-install` (same `CGO_ENABLED=0` flags). Alpine ships the musl loader
  at `/lib/ld-musl-x86_64.so.1`, not `/lib64/ld-linux-x86-64.so.2`.
- Related open PR by the same author: #5801 "build: Reproducible builds"
  (adds `SOURCE_DATE_EPOCH` to `scripts/release.sh`), stale since 2022-04-15.
  Not about hardening flags.
- Duplicate search ("hardening compilation flags pie", "buildmode pie"): no
  other issue or PR. #10836 "harden Go module supply chain" is about
  dependencies, not linker flags.

## Reproduction (if attempted)
Cross-compiled lnd from master 69e359173 (go1.26.8 darwin/arm64 host) for
linux/amd64 with the release tags, once with the current release flags and
twice with `-buildmode=pie` added. No lnd files changed; `git status` clean.

```
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \
  -ldflags="-s -w -buildid=" -tags="<release tags>" -o lnd-exe ./cmd/lnd
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -buildmode=pie \
  -ldflags="-s -w -buildid=" -tags="<release tags>" -o lnd-pie ./cmd/lnd
```

| binary | `file` output | size |
|---|---|---|
| lnd-exe (current flags) | ELF 64-bit LSB executable, statically linked, stripped | 69,562,494 |
| lnd-pie (`-buildmode=pie`) | ELF 64-bit LSB pie executable, dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, stripped | 76,501,258 |

- PIE builds fine with `CGO_ENABLED=0` and the internal linker; no cgo or
  external toolchain needed. Same result on linux/arm64 (interpreter
  `/lib/ld-linux-aarch64.so.1`).
- Reproducibility holds: two independent PIE builds produced identical
  sha256 `c18c2f67...3104a5`.
- Size grows by about 10% (6.9 MB) because of relocation tables.
- The PIE binary declares a glibc program interpreter even though it links
  no shared libraries. It will fail to exec on a system without
  `/lib64/ld-linux-x86-64.so.2`, which includes the Alpine image lnd ships in
  Docker and any `scratch`/distroless container. The current static binary
  runs anywhere.
- Not covered: runtime behaviour of the PIE binary on a glibc host (no Linux
  box in this session), and performance; Go PIE overhead on amd64 is
  generally small but was not measured.

## Assessment for the human
This is a generic checklist pasted from a CNCF thread that itself went
nowhere. Nothing in it is a bug. Concretely for lnd:
1. Already done or not applicable: symbols stripped, `-trimpath`,
   `-mod=readonly`, NX; RELRO/RPATH/FORTIFY/stack canary are C-toolchain
   concepts with no counterpart in a static Go binary; `CGO_ENABLED=1` plus
   external linking would undo lnd's static, reproducible release builds.
2. The single actionable item is `-buildmode=pie` for the Linux release
   binaries (ASLR for the executable image). It works and stays reproducible,
   but it costs 10% size and, more importantly, makes the Linux binary depend
   on a glibc dynamic loader, so it would break the Alpine Docker image and
   anyone running lnd in a minimal container. Given that Go is memory-safe
   and lnd's realistic attack surface is network protocol and RPC logic, not
   memory corruption, the benefit is marginal.

Recommendation: close as not planned with the push-back comment below. If a
maintainer does want PIE, open a narrowly scoped issue for "evaluate
`-buildmode=pie` for Linux release binaries" that names the Docker/static
tradeoff; this issue's title and body are too broad to act on.

## Draft comment
Closing this as not planned. Most of the flags in this list are for C
programs that link against a system libc, and lnd's release binaries are
static Go executables built without cgo, so RELRO, RPATH, FORTIFY and stack
canaries have nothing to act on. The items that do apply are already in
place: release builds use `-trimpath`, strip symbols, and are reproducible;
Windows and macOS builds are already position independent. The one remaining
option, PIE for the Linux binaries, builds fine but makes the binary depend
on the glibc dynamic loader, which would break the Alpine Docker image and
minimal containers, for a small gain on a memory-safe language. If someone
wants to pursue PIE specifically, a scoped issue that addresses that tradeoff
would be the way to do it.
