## Summary
Joost's 2020 brainstorm: probing an MPP destination part-by-part with unknown
hashes proves nothing, because the receiver cancels each part before the set is
complete, so two sequential 20 sat probes "succeed" through a 20 sat channel
that can never carry 40 sat at once. The ask is a receiver-cooperative probe
(a `probe` TLV or an AMP trick) where the receiver holds parts until the set
completes, then fails the set. `EstimateRouteFee` probing (#8136, v0.18) does
not cover this: it is hardcoded to a single part. Whether lnd wants MPP probing
at all is a product call.

## Evidence
- `lnrpc/routerrpc/router_server.go:562-565`: the probe request built by
  `probePaymentRequestWithSender` sets `MaxParts: 1`. The LSP-probe path at
  `:646` copies the same value. So `EstimateRouteFee` with a payment request
  probes single-shot only, and cannot report whether an amount that needs
  splitting is payable.
- #7916 (the scoping issue for #8136, closed 2024-03-05) explicitly listed
  "Multi-part payment probing (#4219)" under long-term, out-of-scope work.
- #9942 (TrezorHannes, 2025-06-12, open, no comments) asks for the RPC-level
  version of this: `estimateroutefee` that considers MPP and accepts outgoing
  channels. The outgoing-channel half has since landed
  (`RouteFeeRequest.outgoing_chan_ids`, `router.proto:415`); the MPP half has
  not.
- Roasbeef (2021-08-31, MEMBER): "Possible now via AMP, but not yet manifested
  on the RPC interface." Suggested a first-class probing API that sends an
  invalid share as the last shard. No follow-up in five years.
- An application cannot work around this with what lnd exposes today: a
  `SendPaymentV2` with a random hash and `max_parts > 1` fails each shard at
  the receiver immediately, which is exactly the flaw the issue describes.
  Fixing it needs the receiver to hold parts for an unpayable set, i.e. a
  protocol signal.
- The 2026-04-27 comment from "AgentRoute Oracle" is vendor spam; hide it.

## Decision for the human
Do we want lnd to offer a true multi-part probe, which requires either a new
receiver-side signal (non-standard TLV, or spec work) or an AMP-based trick on
the sender side? If no: close as not planned, do not cite `EstimateRouteFee`
as covering it, because it does not. If maybe: close this one and let #9942
carry the ask, since it is phrased against the current RPC; add a note there
linking Joost's point that sequential single-part probes are not a valid MPP
check. If yes: keep open, label it the tracker, and link #9942 as a duplicate.

## Decision
Option 2: close this issue and let #9942 carry the ask. A separate note on
#9942 pointing at Joost's sequential-probe argument is a follow-up, not drafted
here.

## Draft comment
Closing this in favour of #9942, which covers the same ask against the RPC we have today. lnd now has payment probing through EstimateRouteFee, but it deliberately sends a single part, so it cannot tell you whether a payment that needs to be split will succeed. The point made in the first comment still stands: probing the parts one at a time does not prove anything, because the receiver cancels each part before the full set arrives. A real multi-part probe needs the receiver to hold the parts until the set is complete, and there is no way to ask for that in the Lightning protocol today, so this most likely needs a spec change before lnd can build it. #9942 is where the sender-side part of the discussion lives, but there is no timeline for it.
