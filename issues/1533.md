## Summary
Request (Jul 2018, lnd v0.4.2): when bitcoind is still starting and answers RPC
calls with `-28: Loading block index...`, lnd exits immediately; it should wait
instead, like `bitcoin-cli -rpcwait`. Since lnd v0.17.1 the startup check
retries on error -28 once a second for up to 30 seconds, so the immediate exit
in the report no longer happens. The wait is capped and not configurable, so a
bitcoind that needs longer than 30 seconds to warm up still makes lnd exit;
that is why confidence is medium rather than high.

## Evidence
- Every failure log in the thread predates the fix: reporter on v0.4.2 (2018),
  seth586 on v0.15.5 (Mar 2023, worked around it with `sleep 10`). schildbach
  (May 2023) describes a hypothetical 15-minute bitcoind startup, no log.
- btcwallet#891 (yyforyongyu, merged 2023-10-17), commit `148ac237b` "chain:
  wait for `bitcoind` to finish loading blocks during startup". PR body: "It
  also fixes the case where `bitcoind` is still loading blocks, causing the
  `NewBitcoindConn` to return an error."
- Picked up by lnd #8094 "gomod: update btcwallet re rescan race fix", merged
  2023-10-18, milestone v0.17.1. `go.mod` at tag v0.17.0-beta pins btcwallet
  `…20230804184612-07be54bc22cf` (without the fix); v0.17.1-beta pins
  `…20231017144732-e3ff37491e9c` (with it). Not mentioned in the lnd release
  notes.
- Code on the btcwallet version lnd master pins
  (`v0.18.1-0.20260903142755-a960541f35ed`, which is also btcwallet master
  `a960541f3`), `chain/bitcoind_conn.go`:
  - `:48` `errStillLoadingCode = "-28"`, `:52` `bitcoindStartTimeout = 30 * time.Second`
  - `:336` `getBlockHashDuringStartup` retries `getblockhash 0` every second
    while the error contains "-28", returns `ErrBitcoindStartTimeout` after 30s.
  - `:160` `NewBitcoindConn` calls it (via `getCurrentNet`) as its first RPC.
- lnd side: `chainreg/chainregistry.go:364` calls `chain.NewBitcoindConn`; an
  error bubbles up through `config_builder.go:679` ("unable to create partial
  chain control") and `cmd/lnd/main.go` exits with code 1. lnd has no warm-up
  handling of its own (no match for `InWarmup`/`warmup` in lnd Go code) and no
  config option for the timeout.
- If bitcoind is not listening yet at all (connection refused), btcd's
  rpcclient retries the HTTP POST 10 times with linear backoff (btcd#1743,
  merged 2021-11-16; `rpcclient/infrastructure.go:96,104`), about 22 seconds.
- The alternative fix referenced in the thread, btcwallet#677 (sangaman, waits
  indefinitely), was approved by halseth and wpaulino but never merged; last
  activity 2023-05-15. It is superseded in practice by #891.
- Maintainer position on longer outages: guggero (2020-11-30, in-thread) and
  Roasbeef (2021-08-25, on #5661) both point to restarting lnd from a
  supervisor. `contrib/init/lnd.service:19-20` ships `Restart=on-failure`,
  `RestartSec=60`, which works here because the exit code is 1.
- Related: #5661 closed 2026-02-21 as duplicate of #5625 (open), which tracks
  exit codes when lnd shuts down because of bitcoind problems at runtime. That
  is a different case from startup warm-up. No newer duplicate of this request
  found ("warmup", "Loading block index", "Verifying blocks").

package issue1533

import (
	"encoding/json"
	"errors"
	"fmt"
	"net"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"
	"time"

	"github.com/btcsuite/btcd/chaincfg/v2"
	"github.com/btcsuite/btcwallet/chain"
)

// fakeBitcoind answers every RPC with "-28: Loading block index…" (HTTP 500,
// as bitcoind does) until warmup has elapsed. After that it answers
// getblockhash with the regtest genesis hash and fails everything else with a
// marker error, so the test can tell that startup got past the warm-up check.
func fakeBitcoind(warmup time.Duration) *httptest.Server {
	start := time.Now()

	return httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter,
		r *http.Request) {

		var req struct {
			ID     json.RawMessage `json:"id"`
			Method string          `json:"method"`
		}
		_ = json.NewDecoder(r.Body).Decode(&req)

		w.Header().Set("Content-Type", "application/json")
		switch {
		case time.Since(start) < warmup:
			w.WriteHeader(http.StatusInternalServerError)
			fmt.Fprintf(w, `{"result":null,"error":{"code":-28,`+
				`"message":"Loading block index…"},"id":%s}`,
				req.ID)

		case req.Method == "getblockhash":
			fmt.Fprintf(w, `{"result":"%s","error":null,"id":%s}`,
				chaincfg.RegressionNetParams.GenesisHash, req.ID)

		default:
			w.WriteHeader(http.StatusInternalServerError)
			fmt.Fprintf(w, `{"result":null,"error":{"code":-1,`+
				`"message":"past warmup"},"id":%s}`, req.ID)
		}
	}))
}

func connect(host string) (time.Duration, error) {
	start := time.Now()
	_, err := chain.NewBitcoindConn(&chain.BitcoindConfig{
		ChainParams: &chaincfg.RegressionNetParams,
		Host:        host,
		User:        "u",
		Pass:        "p",
		PollingConfig: &chain.PollingConfig{
			BlockPollingInterval: time.Second,
			TxPollingInterval:    time.Second,
		},
	})

	return time.Since(start), err
}

// A warm-up shorter than 30s is waited out.
func TestShortWarmup(t *testing.T) {
	srv := fakeBitcoind(5 * time.Second)
	defer srv.Close()

	took, err := connect(strings.TrimPrefix(srv.URL, "http://"))
	t.Logf("took=%v err=%v", took.Round(time.Millisecond), err)

	if err == nil || !strings.Contains(err.Error(), "past warmup") {
		t.Fatalf("expected to get past warm-up, got: %v", err)
	}
	if took < 5*time.Second {
		t.Fatalf("returned before warm-up ended: %v", took)
	}
}

// A warm-up longer than 30s makes startup fail.
func TestLongWarmup(t *testing.T) {
	srv := fakeBitcoind(time.Hour)
	defer srv.Close()

	took, err := connect(strings.TrimPrefix(srv.URL, "http://"))
	t.Logf("took=%v err=%v", took.Round(time.Millisecond), err)

	if !errors.Is(err, chain.ErrBitcoindStartTimeout) {
		t.Fatalf("expected start timeout, got: %v", err)
	}
	if took < 29*time.Second || took > 35*time.Second {
		t.Fatalf("unexpected wait: %v", took)
	}
}

// bitcoind not listening at all: how long until startup gives up.
func TestNotListening(t *testing.T) {
	l, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		t.Fatal(err)
	}
	addr := l.Addr().String()
	l.Close()

	took, err := connect(addr)
	t.Logf("took=%v err=%v", took.Round(time.Millisecond), err)

	if err == nil || !strings.Contains(err.Error(), "connection refused") {
		t.Fatalf("expected connection refused, got: %v", err)
	}
}

## Assessment for the human
The reported behaviour (instant exit on -28) is gone since v0.17.1. What
remains is the literal ask, an open-ended wait like `-rpcwait`: lnd gives up
after 30 seconds and relies on the service manager to restart it. Options:
1. Close as completed, citing v0.17.1 and the restart setup for slow nodes
   (draft below). Matches how #3985 was handled.
2. Keep open and retitle to the narrower ask, a configurable or unlimited
   warm-up wait. This would need a btcwallet change plus an lnd config option.

## Decision
Closed as completed on 2026-09-30 (option 1); comment posted.

## Draft comment
Closing this, because lnd has waited for bitcoind to warm up since v0.17.1
(btcsuite/btcwallet#891). If bitcoind answers with "-28: Loading block
index..." or "Verifying blocks..." at startup, lnd now retries every second
for up to 30 seconds instead of exiting right away. If bitcoind needs longer
than that, lnd still exits with an error, and a service manager set to restart
on failure (as in the sample systemd unit in `contrib/init`) will bring it
back up once bitcoind is ready. If 30 seconds is too short for your setup on a
current lnd version, please open a new issue with your bitcoind startup times.
