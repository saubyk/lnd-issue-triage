## Summary
Request (Sep 2021, naveensrinivasan, same OpenSSF-style batch as #5944, #5966
and #5889): switch the final stage of lnd's Docker image from `alpine` to
Google's distroless images, which are smaller, have no shell or package
manager, and are signed. The stated reason was that the Alpine `latest` tag
was not signed under Docker Content Trust. There are no comments. The only
cross-reference is the reporter's own PR #5753 (pin base images by SHA),
which has sat unreviewed since 2021. On master the final image is still
`FROM alpine`, unpinned. Distroless would break a documented feature: the
image deliberately ships `bash`, `gnupg`, `wget` and `jq` so users can run
`/verify-install.sh` inside the container to check the release signatures.
The binaries are static (`CGO_ENABLED=0`), so anyone who wants a minimal
image can copy them onto `distroless/static` or `scratch` themselves. Product
call. Recommend closing as not planned.

## Evidence
- `Dockerfile` (master `c03d36598`):
  - Builder: `golang:1.27.3-alpine`, then `make release-install`.
  - Final: `FROM alpine as final`, an untagged and therefore floating
    `latest` with no digest pin. Adds `bash jq ca-certificates gnupg wget`
    with the comment "We also require wget and gpg for the signature
    verification script". Copies `scripts/verify-install.sh` and
    `scripts/keys/*` into the image. `ENTRYPOINT ["lnd"]`.
- `scripts/verify-install.sh` is `#!/bin/bash` and calls `gpg` (:81-88),
  `wget` (:96, :106, :123) and `jq` (:101-118). None of these exist in
  `distroless/static`, which has no shell.
- The in-container verification is documented: `docs/DOCKER.md:68` and
  `docs/release.md:102` both say `docker run --rm --entrypoint=""
  lightninglabs/lnd:<tag> /verify-install.sh <tag>`.
- `docker exec ... lncli` (`docs/DOCKER.md:96`) would keep working on
  distroless, since `lncli` is a static binary. Anything users run through a
  shell in the container would not.
- `dev.Dockerfile` also uses `FROM alpine` with `bash jq`. jq was re-added on
  2026-10-20 (#11352), a sign people script inside the dev image.
- Published image: `.github/workflows/docker.yml` builds the root
  `Dockerfile` for `linux/amd64,linux/arm64` and pushes `lightninglabs/lnd`
  on tags and as a daily build. There is no image signing step (cosign or
  similar). Signing the image itself is #5728 (open, 2021, same reporter).
- #5753 "docker: Pinned images by SHA" (open, no reviews, merge conflicts).
  It pins only the builder images (`golang:1.16.3-alpine` in `Dockerfile` and
  `dev.Dockerfile`, `golang:1.16.3-buster` in `make/builder.Dockerfile`) to
  2021 digests. It does **not** pin the final `FROM alpine` stage. thinkmassive
  (2021-10-14) raised that pinning by digest needs to keep working for both
  amd64 and arm64; the reporter suggested `ko`. Nothing since.
- Related open items from the same batch: #5728 (sign docker containers) and
  #5889 (vendored actions, still-valid). #5966 (hardening flags) closed not
  planned on 2026-10-28.

## Draft comment
Proposed close as not planned:

> Closing this as not planned. The lnd Docker image is built on Alpine on
> purpose: it includes a shell and the tools (`gpg`, `wget`, `jq`) needed to
> run `/verify-install.sh` inside the container, which checks the release
> signatures and is the documented way to verify the image (see
> `docs/DOCKER.md`). A distroless image has no shell, so that check would
> stop working. The `lnd` and `lncli` binaries are fully static, so anyone who
> wants a minimal image can copy them onto `gcr.io/distroless/static` or
> `scratch` in a two-line Dockerfile of their own.

## Note for the human
Product call. Options:
1. **Close as not planned** (recommended) with the draft above.
2. **Keep open and do it:** ship a second, distroless variant tag (e.g.
   `lightninglabs/lnd:<tag>-distroless`) next to the Alpine one. It's cheap to
   build but doubles the published images to maintain.

Separately, the real low-cost gap is that the final stage is
`FROM alpine` with no tag or digest. Every daily and release build picks up
whatever Alpine `latest` is that day, which hurts reproducibility of the
image. Pinning it (at least `alpine:3.x`, ideally a multi-arch digest) is
worth doing. Correction (2026-10-28): #5753 does not cover this. It pins
only the 2021 Go builder images, so no PR addresses the final stage.
