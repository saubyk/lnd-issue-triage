## Summary
Muun settled incoming HTLCs via the interceptor RPC and expected them in
`fwdinghistory` for accounting. Roasbeef declined in-thread (2021-01-18): an
interceptor settle is not a forward as lnd defines it, so it will not appear in
`ForwardingHistory`; use `SubscribeHtlcEvents` instead. The reporter accepted
("Perfect! We can make do with that."). The behaviour is unchanged on master,
and the reporter's underlying need, a durable record that the SETTLE actually
took effect, has since been met by the final HTLC resolution work in v0.16.

## Evidence
- Behaviour unchanged on master. `interceptedForward.Settle` builds an
  `UpdateFulfillHTLC` packet and hands it straight to the incoming link via
  `mailOrchestrator.Deliver` (`htlcswitch/interceptable_switch.go:979-1006`).
  It never passes through `Switch.handlePacketSettle`, which is the only place
  a `ForwardingEvent` is appended, and that code additionally requires
  `circuit.Outgoing != nil` (`htlcswitch/switch.go:3146-3170`). An intercepted
  HTLC that is settled locally has no outgoing circuit, so nothing is logged.
- Maintainer decision: Roasbeef, MEMBER, 2021-01-18: "A forward as defined
  within lnd is something that enters and exits lnd via the existing automated
  process ... the class of transactions you're referring to won't show up in
  ForwardingHistory ... you'll need to externally account for this."
  Reporter's reply the next day: "Perfect! We can make do with that."
- What now covers the real concern (is the settle recorded anywhere?):
  - #6517 "htlcswitch: final settle signal", merged 2022-10-27, v0.16.0.
    The link calls `HtlcNotifier.NotifyFinalHtlcEvent` and persists
    `FinalHtlcInfo` when an incoming HTLC leaves the commitment
    (`htlcswitch/link.go:4449-4456`). This is link-level, so interceptor
    settles are covered.
  - `SubscribeHtlcEvents` emits `FinalHtlcEvent{settled, offchain}`
    (`lnrpc/routerrpc/router.proto:844`).
  - `LookupHtlcResolution` RPC (#7467, v0.16.0) returns the persisted outcome
    by channel id and HTLC index. Opt-in via `store-final-htlc-resolutions`.
  - Release note: `docs/release-notes/release-notes-0.16.0.md:86-99`.
- Cross-refs #6040 and #6208 are both closed completed; #6208 was closed by
  #6517 above. No newer open issue asks for interceptor settles in
  `fwdinghistory`.
- No activity since 2023-08 label change; reporter last wrote 2021-01-19.

## Draft comment
Closing this. Roasbeef's answer from January 2021 still stands: an HTLC that your application settles through the interceptor is not a forward from lnd's point of view, so it does not appear in fwdinghistory, and that is not going to change. What did change is that lnd can now tell you whether such a settle actually went through. Since v0.16, lnd can record the final outcome of every incoming HTLC once it leaves the channel (turn on store-final-htlc-resolutions in lnd.conf), and you can read it back with the LookupHtlcResolution RPC or watch for it live through SubscribeHtlcEvents; see #6517 for the details. That covers the accounting gap you described, without treating these HTLCs as forwards.
