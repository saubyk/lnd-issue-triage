## Summary
Request (May 2020, lnd v0.10.0): change RPC fields that can never be negative
(dates, amounts, confirmation counts) from `int64` to `uint64`/`uint32` in the
`.proto` files. Nothing was changed, and in March 2025 a maintainer (guggero)
declined it in the thread: the types are not ideal, but changing them would
break existing client software, and backward compatibility matters more. The
contributor who had offered to do the work agreed it was a lot of work for
little reward.

## Evidence
- Maintainer decision, guggero (MEMBER), 2025-03-31: "Even though I agree this
  isn't super nice on the gRPC level, I'm not sure if looking into this is
  really worth the hassle. Especially since you cannot control what the client
  software version is using", and in a follow-up the same day: "It's a bit
  annoying and ugly at times. But not breaking backward compatibility is just
  way more important. You'll probably find many inconsistencies and things
  that could be nicer, but we can't just change them without breaking older
  clients."
- bartoli (who volunteered that day) replied: "I do agree it looks to be a
  good amount of work for little rewards." and said he might instead review
  how the server handles improper values. No PR from him on this followed
  (his only lnd PRs are #7970 and #9657, both unrelated).
- Earlier support: cfromknecht (2020-06-04) agreed and suggested considering
  it for 0.12 as a "pseudo-breaking change" with lead time. It was never
  scheduled; the 2025 exchange is the later and current position.
- The specific risk guggero names: a client compiled against the old proto
  that sends `-1` in a field the server now reads as unsigned would be seen as
  a very large number.
- Master is unchanged: the fields cited in the issue are still signed in
  `lnrpc/lightning.proto` (`Invoice.value` :3857, `creation_date` :3878,
  `settle_date` :3885, `amt_paid_sat` :3953, `Utxo.confirmations` :720).
  `lightning.proto` has 127 `int64` and 127 `uint64` fields.
- `docs/review.md:106` lists avoiding breaking changes for existing API users
  as a review criterion.
- No cross-referenced PRs, no PR found for "int64 uint64 proto", no duplicate
  issue.
- No reproduction: this is a design request, not a bug.

## Decision
Closed as not planned on 2026-09-30, following the maintainer decline in-thread; comment posted.

## Draft comment
Closing this as not planned, following @guggero's assessment above. The request is fair: some fields that can never be negative are declared as signed numbers. But changing their type would break wallets and tools built against the current API definitions, and as he put it, "not breaking backward compatibility is just way more important". Applications should keep treating these fields as non-negative values on their side.
