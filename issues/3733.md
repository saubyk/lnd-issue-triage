## Summary
Bug report (Nov 2019, lnd v0.8.1, no comments since): a routerrpc SendPayment
with `cltv_limit` below the final CLTV delta was accepted and the payment went
out with a high time lock, instead of the request being refused. Since lnd
v0.13.0 the request is refused up front: `cltv_limit` must be greater than
the final CLTV delta plus 3 blocks of padding, which is exactly the threshold
the reporter identified.

## Evidence
- Cause in v0.8.1: `routing/payment_session.go:79` computed
  `cltvLimit := payment.CltvLimit - uint32(finalCltvDelta)` (after adding the
  3-block `BlockPadding`) with no bounds check. Both are unsigned, so a limit
  below delta + 3 wrapped around to a huge value and no limit was enforced.
- Fix: PR #5293 "multi: validate payment params at RPC layer" (Crypt-iQ),
  merged 2021-05-13, milestone 0.13.0, commit `a70d0bef3`. It does not
  reference this issue. `routing.ValidateCLTVLimit` is absent at tag
  v0.12.0-beta and present at v0.13.0-beta.
- On master: `routing/payment_session.go:25` `ValidateCLTVLimit` returns
  "cltv limit %v should be greater than %v" when `limit <= delta (+ padding)`.
  Called for SendPaymentV2 in `lnrpc/routerrpc/router_backend.go:1294` with
  padding, before the payment is started, and for QueryRoutes at `:397`
  without padding.
- The same subtraction still exists at `routing/payment_session.go:276`, but
  it can no longer wrap because the request is rejected first.
- Existing unit test `routing/payment_session_test.go:17`
  `TestValidateCLTVLimit` covers the boundary (103 rejected, 104 accepted for
  delta 100); it passes on master.
- Thread: zero comments, zero cross-references. No duplicate found.

func TestIssue3733(t *testing.T) {
	destNodeBytes, err := hex.DecodeString(destKey)
	require.NoError(t, err)

	for _, limit := range []int32{1, 39, 40, 43, 44, 100} {

## Draft comment
Closing this, because it was fixed in lnd v0.13.0 by #5293. SendPayment now refuses the request up front if `cltv_limit` is not greater than the final CLTV delta plus the 3 blocks of padding lnd adds, and returns an error such as "cltv limit 40 should be greater than 43". I confirmed this on current master. If you still see a payment go out with a time lock above your limit on a current version, please reopen with the request you sent.
